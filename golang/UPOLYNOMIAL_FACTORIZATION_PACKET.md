## Real prerequisites and proposed storage gate

Existing exact numerical core algorithms provide Int/IntegerModular owners, Copy/Set/Power/Root/PerfectSquare/Divides, AddMul/SubMul, scalar polynomial Mul/Div, normalize/content, derivative, all GCD/ExtendedGCD/DivRem/ExactDiv and source Power, plus actual resource/cooperation callbacks. Root isolation does not replace factorization. Registered factorization depends on **prime_generator.cpp**, not the already ported active big-prime literal table used by modular GCD.

The coefficient-storage prerequisite is real: Hensel constructs sibling `core_manager` objects over the same underlying integer owner, then passes their raw coefficient buffers among integer/prime/composite-modulus cores. Current `UPolynomialView` and `upolyVectorState` resolve through a manager-local backing directory and origin, so directly using foreign views is rejected. Deep-copying a foreign input, changing an existing core's modulus temporarily, or constructing a fake manager to route reads would add/remove source actions.

**Recommended storage design to approve before coding:** extract the concrete charged backing directory into an owner-local `upolyCoefficientStore`, distinct from each arithmetic core's manager origin, descriptor pages, cached vectors, modulus and scratch. Related real core constructors borrow one actual store plus the same IntegerManager/resource/cooperation owners; public scalar views bind store origin/backing/generation, public polynomial descriptors still bind their own manager origin/slot/generation. Arithmetic uses the receiver's actual modulus/scratch while resolving shared physical coefficient storage. Each core frees only its own lexical/cache/descriptors; shared store retains directory storage until its last real owner closes, without freeing another core's live coefficient roots. Full actual store/directory/header/backing/retain counts are charged once. No mutable global registry or per-coefficient pointers/interfaces.

This requires coordinated existing changes in `upolynomial.go`, `upolynomial_storage.go`, `upolynomial_modes.go` (Stats attribution), and relevant checked view/origin fixtures; **none are authorized yet**. A private/public related-core constructor may share the actual store; normal existing constructors remain valid owners. A separate decision is needed for source-allowed factor Swap across independently constructed storage pools: source swaps data but keeps callback managers. It cannot be implemented as coefficient copies or unconditionally claimed supported. Either approve an actual scalar storage adoption/cohort API covering those owners, with measured/failure-atomic directory-transfer adapter, or explicitly leave that general-domain branch partial. Selected source calls all use related cores sharing one integer owner; this question does not justify replacing/skipping any Berlekamp/Hensel/recombination body. This proposal does not silently claim general cross-pool completeness.

`UPolynomialFactors` cold owner: self guard, borrowed actual arithmetic manager, shared storage binding, typed outer `[]upolyVectorState` and its size/initialized metadata, independent uint32 multiplicity vector, actual Int constant, uint32 total-factors/total-degree, charged header, closed state. Hot nested records are only scalar backing/generation/size/capacity/initialized fields; actual Int arrays live in shared charged storage. Outer selected source LP64 `sizeof(numeral_vector)=8`, header8, nontrivial move path; degrees stride4/header8. Preserve each vector's geometric2→3→5 source uint32 arithmetic separately from actual Go stride/host domain guards. Capacity-grown outer arrays move scalar ownership ascending, never clone numerals. Clear frees each inner array via source vector destructor while retaining outer/degrees capacity. No flat sequence substitute that retains all old inner capacities after source destruction.

New degree-set storage is concrete `{words []uint32; numBits,capacity uint32}` in a charged cold/lexical owner; copy includes source capacity/unused words, ShiftRight/OR/AND follow exact bit-vector algorithms. Source realloc can grow in place; explicit Go replacement reserves new while old remains charged, documented physical allocator adapter. Represented-domain guards stop undersized wrapped byte allocation at actual source allocation boundary; unimplemented raw undersized-allocation prefixes remain OPEN, as with committed storage.

Berlekamp owns typed Int matrix and int32 pivots, with full source sizes/capacities/old-new peaks. No uint32-only matrix substitution even when ordinary prime coefficients fit. Iterators own exact bool/int32 arrays, no hot per-selection boxed object. Public factor views are scalar physical views: Move/Swap preserve physical binding, actual inner growth/free invalidates, and raw WithCount checks only actual reads. Accessors returning source references can be explicit owning-copy adapters where public borrowing would escape lifetime, but internal source algorithms must use actual borrowed references, not these copies.
